# ТЗ этапа 2: безопасная запись данных

Статус: **выполнен 24 октября 2026 года**.

## 1. Цель

Устранить три риска сохранности данных:

1. Потерю параллельных изменений при редактировании одной ячейки.
2. Применение устаревшего ответа периодического обновления.
3. Частичное сохранение пакета таймеров при ошибке посередине добавления.

Изменения должны сохранять существующие строки, ключи, флоты и назначения.

## 2. Проблема текущей реализации

### Полное обновление строки

`saveTimerAdminFields` получает один изменённый атрибут, но собирает старую
копию всей строки и передаёт все поля в `update_timer_admin_fields`. Параллельное
изменение другого поля может быть незаметно отменено последним запросом.

### Гонка чтения

`loadTimers` вызывается вручную, после сохранений и по интервалу. Запросы не
имеют номера поколения или блокировки. Медленный старый ответ может заменить
более свежий.

### Неатомарное добавление

Массовый ввод вызывает `add_timer` последовательно для каждой разобранной
записи. Ошибка одного запроса не отменяет уже добавленные записи.

## 3. Изменения Supabase

### 3.1. Частичное обновление

Добавить RPC с концептуальной сигнатурой:

```sql
patch_timer_admin_fields(
  p_board_id text,
  p_admin_key text,
  p_id uuid,
  p_changes jsonb,
  p_expected_updated_at timestamptz
)
```

Требования:

- сначала проверять админ-ключ;
- разрешать только поля `title`, `system`, `object_name`, `structure`, `owner`,
  `distance`, `mode`, `end_at`, `note`;
- отклонять неизвестные ключи;
- валидировать структуру, тип таймера, итог и дату так же строго, как текущий RPC;
- менять только переданные поля;
- выполнять update с условием `updated_at = p_expected_updated_at`;
- при конфликте возвращать отдельную понятную ошибку;
- записывать событие результата только при фактическом изменении `note`;
- возвращать актуальную строку таймера.

Старую `update_timer_admin_fields` не удалять в этом этапе, чтобы опубликованный
клиент не сломался до обновления сайта. Её удаление рассматривается отдельной
последующей миграцией.

### 3.2. Атомарное массовое добавление

Добавить RPC:

```sql
add_timers(
  p_board_id text,
  p_admin_key text,
  p_timers jsonb
)
```

Требования:

- принимать только JSON-массив;
- проверять админ-ключ один раз;
- валидировать все обязательные даты и допустимые значения;
- вставлять весь пакет в одной транзакции функции;
- при любой ошибке не сохранять ни одной строки пакета;
- возвращать добавленные таймеры или их количество;
- ограничить разумный размер одного пакета и выдать понятную ошибку при
  превышении.

Старую `add_timer` сохранить для совместимости и локального режима.

## 4. Изменения клиента

### 4.1. Редактирование ячейки

- Передавать в RPC только изменённое поле.
- Передавать `updated_at` строки, на основе которой открыто поле.
- После успеха заменить локальную запись строкой, возвращённой сервером.
- При конфликте не повторять запрос автоматически.
- Показать сообщение: запись уже была изменена, данные обновлены, повторите
  правку при необходимости.
- Загрузить актуальную строку/доску после конфликта.

### 4.2. Защита загрузки

Применить один из эквивалентных вариантов:

- счётчик поколения запроса, позволяющий применить только последний ответ; или
- единый in-flight запрос с пометкой необходимости повторной загрузки.

Дополнительные требования:

- смена ключа доступа аннулирует ответы, запущенные со старым ключом;
- ошибка старого запроса не должна скрывать успешно загруженную новую доску;
- секундный визуальный отсчёт продолжает работать независимо от сетевого poll.

### 4.3. Массовое добавление

- В Supabase-режиме отправлять один RPC `add_timers`.
- В локальном режиме сохранить текущее атомарное добавление в `localStorage`.
- После успеха показывать фактически добавленное количество.
- При ошибке оставлять исходный текст в поле для исправления и повторной
  отправки.
- При отсутствии новой RPC показывать указание обновить `supabase/schema.sql`,
  а не пытаться молча выполнять неатомарный цикл.

## 5. Тестовые сценарии

1. Изменение `system` отправляет только `system` и ожидаемую версию.
2. Одновременное изменение `owner` другим клиентом не затирается.
3. Устаревший `updated_at` вызывает конфликт и обновление отображаемых данных.
4. Изменение `note` создаёт одно событие результата.
5. Повторная установка того же результата не создаёт лишнее событие.
6. Второй сетевой ответ приходит раньше первого; на экране остаются данные
   второго запроса.
7. После смены ключа ответ старого запроса не открывает доску.
8. Пакет из 40 валидных таймеров сохраняется полностью.
9. Один невалидный таймер в пакете приводит к нулю вставленных строк.
10. Ошибка массового добавления не очищает textarea.
11. Старые `add_timer` и `update_timer_admin_fields` остаются доступными до
    завершения переходного периода.
12. Очистка истории и действия командира флота продолжают работать.

## 6. Критерии приёмки

1. Два администратора не могут незаметно затереть разные поля одной строки.
2. Только последний актуальный запрос чтения меняет состояние доски.
3. Массовое добавление обладает семантикой `всё или ничего`.
4. Все тесты этапа 1 и новые проверки проходят локально и в CI.
5. Повторное выполнение обновлённого `supabase/schema.sql` не удаляет данные.
6. В README описана необходимость обновить схему перед публикацией нового JS.
7. Переходные старые RPC остаются работоспособными.
8. Память проекта отмечает этап 2 выполненным и этап 3 текущим.

## 7. Вне объёма этапа

- глобальная оптимизация маршрутов;
- разделение монолитных UI-файлов;
- изменение ролей или формата ключей;
- удаление старых RPC;
- переход на миграционную систему;
- визуальный редизайн.

## 8. Порядок внедрения

1. Добавить тесты конфликтов, гонок и пакетной атомарности.
2. Добавить новые RPC без удаления старых.
3. Обновить клиент на новые RPC.
4. Прогнать полную регрессию.
5. Выполнить схему в тестовом Supabase-проекте поверх существующих данных.
6. Обновить документацию и память проекта.
7. Сначала обновить Supabase пользователя, затем опубликовать новый клиент.

## 9. Результат выполнения

- Добавлена транзакционная RPC `add_timers` с лимитом 100 записей и полной
  проверкой пакета до вставки.
- Добавлена RPC `patch_timer_admin_fields`, разрешающая только известные поля
  и проверяющая ожидаемый `updated_at`.
- Конфликт параллельного изменения возвращает SQLSTATE `40001`, обновляет
  строку на экране и не повторяет запись автоматически.
- Клиент применяет только последний актуальный ответ `get_timers`; смена ключа
  аннулирует начатые со старым ключом запросы.
- Старые `add_timer` и `update_timer_admin_fields` сохранены для совместимости.
- Добавлены браузерные тесты гонок, конфликтов и пакетной записи.
- PGlite выполняет полную схему, пакет из 40 таймеров, откат невалидного пакета,
  журнал результатов и повторное применение схемы без потери строк.
