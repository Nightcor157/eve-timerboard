# ТЗ этапа 3: выделение доменной логики

Статус: **выполнен 24 октября 2026 года**.

## 1. Цель

Отделить правила таймеров, парсер и планировщик маршрутов от DOM и сетевых
вызовов. Пользовательское поведение, внешний вид и схема Supabase на этом этапе
не меняются.

## 2. Целевая структура

```text
js/
  core/
    constants.js
    timer-parser.js
    timer-rules.js
    route-planner.js
  shared/
    format.js
    clipboard.js
    errors.js
  services/
    supabase-api.js
    system-catalog.js
```

`app.js` и `routes.js` остаются временными точками входа до этапа 4, но
используют модули вместо собственных копий правил.

## 3. Объём работ

### 3.1. Константы и форматирование

- вынести допустимые типы структур, стороны таймера и итоги;
- вынести очистку текста, UTC-форматирование и безопасное сравнение;
- генерировать варианты фильтров и редакторов из общих массивов;
- сохранить русские подписи и исторические имена полей базы.

### 3.2. Парсер

- перенести нормализацию переносов, разбиение блоков и разбор одного таймера;
- передавать параметры по умолчанию обычным объектом без обращения к DOM;
- сохранить все поддерживаемые русские, английские и однострочные форматы;
- добавить модульные тесты для известных примеров и ошибочных строк.

### 3.3. Правила жизненного цикла

- вынести расчёт `Активен`, `Скоро`, `Ремонт`, `Ожидание итога`, `Завершён`;
- сохранить 15 минут для обычных структур, 2 часа для Customs Office и
  30 минут для Metenox, IHub, TCU и POS;
- вынести фильтрацию по давности завершения и расчёт обратного отсчёта;
- проверить правила чистыми тестами с фиксированным временем.

### 3.4. Планировщик

- вынести текущую жадную эвристику без изменения результата;
- принимать граф, флоты, таймеры, фильтры и текущее время аргументами;
- возвращать назначения и метрики без DOM, Supabase и ESI;
- закрепить существующие stress-сценарии модульными golden-проверками.

### 3.5. Сервисы

- создать один Supabase-клиент и методы API для доски и маршрутов;
- вынести загрузку каталога систем и поиск пути из UI;
- сохранить текущие RPC, параметры авторизации и обработку конфликтов;
- оставить ESI только резервным источником отсутствующего локального пути.

## 4. Тесты

1. Все примеры README разбираются без браузера.
2. Однострочная Customs Office корректно заполняет поля.
3. Параметры по умолчанию заменяют результат парсинга.
4. Для каждого типа структуры верно рассчитывается дополнительное окно.
5. Результат немедленно завершает таймер.
6. Давность 12/24 часа и остальные интервалы не меняют смысл.
7. Фиксированный набор флотов и целей даёт те же назначения, что до выноса.
8. Фильтры атаки/обороны и объектов сохраняют результат.
9. Общий Supabase API отправляет существующие имена RPC и параметры.
10. Все E2E и PGlite-тесты этапов 1–2 продолжают проходить.

## 5. Критерии приёмки

1. Парсер, жизненный цикл и планировщик тестируются без браузера.
2. В `app.js` и `routes.js` нет собственных копий вынесенных правил.
3. Типы структур в интерфейсе строятся из одного клиентского источника.
4. В браузере создаётся один Supabase-клиент.
5. Результаты существующих smoke- и stress-тестов не меняются.
6. GitHub Pages остаётся статическим сайтом без шага сборки.
7. Память проекта отмечает этап 3 выполненным и этап 4 текущим.

## 6. Вне объёма этапа

- визуальный редизайн;
- новая эвристика распределения;
- SQL-миграции;
- удаление старых RPC;
- объединение всего UI в одну точку входа;
- изменение ролей и ключей.

## 7. Порядок выполнения

1. Зафиксировать модульными тестами парсер и правила времени.
2. Вынести константы, форматирование и парсер.
3. Вынести жизненный цикл.
4. Зафиксировать и вынести текущий планировщик.
5. Объединить Supabase API и каталог систем.
6. Прогнать полную регрессию на desktop и mobile.
7. Обновить документацию, сделать отдельный коммит и публикацию.

## 8. Выполненный результат

- парсер, правила жизненного цикла и текущий планировщик вынесены в `js/core/`;
- общие форматтеры и нормализаторы находятся в `js/shared/format.js`;
- один экземпляр Supabase-клиента и именованные RPC-методы находятся в
  `js/services/supabase-api.js`;
- локальный каталог EVE, BFS и резервные запросы ESI находятся в
  `js/services/system-catalog.js`;
- варианты структур и сторон таймера в интерфейсе создаются из общих констант;
- добавлено 12 модульных тестов, полный набор SQL, PGlite, smoke и stress
  проходит без регрессий.
