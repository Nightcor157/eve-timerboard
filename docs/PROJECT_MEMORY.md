# Память проекта EVE Timerboard

Последнее обновление: 24 октября 2026 года.

Этот файл хранит устойчивый контекст проекта для следующих сессий разработки.
После завершения каждого этапа рефакторинга его необходимо актуализировать.

## 1. Назначение проекта

EVE Timerboard — статический сайт для совместной работы с таймерами структур
EVE Online. Данные хранятся в Supabase, сайт публикуется через GitHub Pages.

Основные возможности:

- парсинг одного или нескольких таймеров из текста EVE;
- общая доска с поиском, сортировкой, CSV и историей;
- ручное редактирование таймеров главным администратором;
- результаты `Защищена`, `Уничтожена` и сброс результата;
- роли зрителя, командира флота и главного администратора;
- общая карта и сохранённые маршруты нескольких флотов;
- фильтрация целей по стороне таймера и типу структуры;
- интерактивная карта на основе EVE SDE.

## 2. Развёртывание

- Репозиторий: `https://github.com/Nightcor157/eve-timerboard.git`.
- Рабочая ветка: `main`.
- GitHub Pages публикует корень ветки `main` автоматически после push.
- Сборщик приложения отсутствует: браузер открывает `index.html`, CSS и JS.
- Основная схема базы: `supabase/schema.sql`.
- В `js/config.js` разрешены только Project URL и Publishable/anon key Supabase.

Админ-ключ, ключ просмотра и ключи флотов не должны попадать в Git. В Supabase
хранятся их bcrypt-хеши; полный ключ флота возвращается только при создании или
ротации.

## 3. Текущая архитектура

| Область | Файл | Ответственность |
|---|---|---|
| Разметка | `index.html` | Доска, админская панель, маршруты, шаблон строки |
| Доска | `js/app.js` | Доступ, парсер, CRUD таймеров, состояния, таблица, CSV |
| Маршруты | `js/routes.js` | Флоты, расчёт, EVE-граф, таблицы, карта, масштабирование |
| Стили | `css/styles.css` | Все стили и адаптивность |
| База | `supabase/schema.sql` | Таблицы, RLS, RPC, ключи и журнал результатов |
| Граф EVE | `data/solar-systems.json` | Системы, координаты, security и связи ворот |
| Регионы | `data/regions.json` | Названия регионов для подписей карты |

Клиентские модули пока являются IIFE-скриптами. `app.js` и `routes.js`
обмениваются событиями `eve-timerboard:*` через `window`. Каждый из них создаёт
собственный Supabase-клиент.

## 4. Роли и доступ

### Зритель

- вводит ключ просмотра;
- видит доску и общую карту;
- не может менять таймеры или открывать закрытый маршрут флота.

### Командир флота

- сначала получает доступ к доске по ключу просмотра;
- выбирает флот и вводит его отдельный ключ;
- видит маршрут только своего флота;
- может ставить или сбрасывать итог только у назначенных этому флоту целей.

### Главный администратор

- проходит серверную проверку админ-ключа;
- добавляет, редактирует и удаляет таймеры;
- меняет ключ просмотра;
- очищает завершённую историю;
- управляет профилями и ключами флотов;
- рассчитывает и смотрит все маршруты.

Параметр `?admin=1` только открывает окно входа и не предоставляет права сам по
себе. Авторизация защищённых действий выполняется RPC-функциями Supabase.

## 5. Модель таймера

Исторические имена колонок сохранены для совместимости:

| Интерфейс | `public.timers` |
|---|---|
| Корпорация | `title` |
| Система | `system` |
| Объект | `object_name` |
| Структура | `structure` |
| Альянс | `owner` |
| Атака / Оборона | `distance` |
| Режим | `mode` |
| Укреплён до | `end_at` |
| Итог | `note` |

Разрешённые итоги: пусто, `Защищена`, `Уничтожена`.

## 6. Жизненный цикл таймера

- До `end_at`: `Активен` или `Скоро`, если осталось не больше четырёх часов.
- Обычные структуры после `end_at`: фаза `Ремонт` 15 минут.
- `Customs Office`: фаза `Ремонт` 2 часа.
- `Metenox Moon Drill`, `IHub`, `TCU`, `POS`: ожидание итога 30 минут.
- Поставленный итог немедленно переводит запись в завершённые.
- Без итога запись становится завершённой после своего дополнительного окна.

До выполнения этапа 3 эти правила продублированы в `js/app.js` и RPC очистки
истории в `supabase/schema.sql`. Любое изменение необходимо синхронно вносить в
оба места и проверять тестом очистки истории.

## 7. Маршрутизация

Текущий планировщик — детерминированная жадная эвристика:

1. Берёт будущие цели без результата, прошедшие фильтры.
2. Сортирует цели по `end_at`.
3. Для каждой цели считает путь каждого флота от его текущей конечной точки.
4. Выбирает вариант без опоздания, затем с меньшим опозданием/ETA/числом
   прыжков.
5. Обновляет положение и доступное время выбранного флота.

Это не глобальный оптимизатор VRPTW. Он не пересматривает прошлые назначения и
может уступать более сложному распределению в тесных временных окнах.

Основной маршрут строится по локальному графу SDE. ESI используется как
резервный источник, если локальный путь отсутствует.

- тесты доски, админского вида, командира, общей карты и очистки истории

Ограничение: существующие Playwright-скрипты находятся вне репозитория и
содержат абсолютные пути этого компьютера. Новый клон и GitHub Actions пока не
могут запустить их воспроизводимо.

## 9. Известные технические риски

1. Изменение одной ячейки отправляет все поля таймера и может затереть
   параллельное изменение другого администратора.
2. Периодические `get_timers` могут выполняться параллельно; старый ответ может
   прийти после нового.
3. Массовое добавление выполняет отдельный RPC на каждый таймер и допускает
   частично сохранённый пакет.
4. `routes.js`, `app.js` и `styles.css` стали крупными монолитными файлами.
5. Типы структур и некоторые утилиты продублированы в HTML, JS и SQL.
6. Тесты и CI не хранятся в репозитории.
7. Supabase JS подключён с CDN по плавающей версии `@2`.
8. SQL хранится одним снимком без последовательной истории миграций.
9. Стресс-тест проверяет целостность назначений, но пока не доказывает качество
   оптимизации и не считает опоздания нарушением.

## 10. Принятые решения рефакторинга

- Не переписывать приложение целиком.
- Не добавлять React, Vue или другой UI-фреймворк без отдельной причины.
- Сохранить статическую публикацию GitHub Pages.
- Использовать нативные ES-модули для разделения кода.
- Сначала создать воспроизводимую систему тестов, затем менять поведение.
- Делить изменения на небольшие этапы с отдельной проверкой и коммитом.
- Сохранить полный `supabase/schema.sql` для простой установки, даже после
  появления каталога миграций.
