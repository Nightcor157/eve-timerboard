# План рефакторинга EVE Timerboard

## 1. Цель

Снизить риск регрессий после частых изменений, разделить бизнес-логику и UI,
устранить небезопасные сценарии записи и сохранить простое развёртывание через
GitHub Pages + Supabase.

Рефакторинг считается успешным, если приложение сохраняет текущее поведение,
а основные правила можно проверять без запуска всей страницы и без абсолютных
путей конкретного компьютера.

## 2. Основные принципы

- Без полной переписи и длительной отдельной ветки.
- Один этап — одна понятная группа рисков.
- До изменения поведения сначала добавляется тест.
- Каждая версия после этапа остаётся пригодной для публикации.
- Изменения БД сохраняют существующие таймеры, ключи, флоты и назначения.
- Интерфейсные права всегда дублируются серверной проверкой RPC.
- Пользовательская документация обновляется вместе с поведением.

## 3. Этапы

### Этап 0. Аудит и документация

Статус: **выполнен**.

Результат:

- описана текущая архитектура и роли;
- перечислены технические риски;
- создана память проекта;
- подготовлены ТЗ этапов 1 и 2;
- определён порядок дальнейшего рефакторинга.

### Этап 1. Тестовый фундамент

Статус: **выполнен**.

Подробное ТЗ: `docs/REFACTORING_STEP_01_TEST_FOUNDATION.md`.

Результат этапа:

- тесты находятся в репозитории;
- отсутствуют абсолютные локальные пути;
- одной командой запускаются синтаксические и браузерные проверки;
- GitHub Actions проверяет изменения в `main` и pull request;
- текущие пользовательские сценарии зафиксированы до структурных изменений.

### Этап 2. Безопасная запись данных

Статус: **выполнен**.

Подробное ТЗ: `docs/REFACTORING_STEP_02_DATA_SAFETY.md`.

Результат этапа:

- изменение одной ячейки не перезаписывает остальные поля;
- конфликт параллельного редактирования обнаруживается;
- автообновление не применяет устаревший ответ;
- пакет таймеров сохраняется полностью или не сохраняется совсем;
- существующие данные и старые клиенты не ломаются во время обновления.

### Этап 3. Выделение доменной логики

Статус: **выполнен**.

Подробное ТЗ: `docs/REFACTORING_STEP_03_DOMAIN_MODULES.md`.

Предлагаемая структура:

```text
js/
  core/
    constants.js
    timer-parser.js
    timer-rules.js
    route-planner.js
  shared/
    format.js
    clipboard.js
    errors.js
  services/
    supabase-api.js
    system-catalog.js
```

Работы:

- вынести парсер в чистый модуль без DOM;
- вынести расчёт состояния таймера и окон ремонта;
- вынести планировщик маршрутов в чистую функцию;
- объединить форматирование, экранирование и буфер обмена;
- создать один Supabase-клиент и типизированные по назначению методы API;
- генерировать элементы фильтров из одного списка структур на клиенте.

Критерий завершения: парсер, жизненный цикл и планировщик проверяются модульными
тестами без браузера и Supabase.

### Этап 4. Разделение интерфейса и карты

Статус: **выполнен**.

Подробное ТЗ: `docs/REFACTORING_STEP_04_UI_SPLIT.md`.

Предлагаемая структура:

```text
js/ui/
  access-view.js
  board-view.js
  timer-editor.js
  fleet-admin-view.js
  route-table-view.js
  route-map-view.js
  system-autocomplete.js
```

Работы:

- разделить состояние доски и маршрутов;
- заменить неявные глобальные события небольшим явным контроллером приложения;
- отделить SVG-карту от загрузки данных и расчёта маршрута;
- разбить CSS по областям без изменения текущего оформления;
- оставить один входной файл `main.js`.

Критерий завершения: изменение карты не требует правок в управлении флотами, а
изменение таблицы не затрагивает расчёт маршрута.

### Этап 5. Единая схема и усиление безопасности

Статус: **выполнен**.

Подробное ТЗ: `docs/REFACTORING_STEP_05_MIGRATIONS_SECURITY.md`.

Работы:

- поддерживать единственный полный `supabase/schema.sql` для новой установки и
  обновления существующей базы;
- закрепить точную версию Supabase JS;
- добавить Content Security Policy после проверки совместимости;
- увеличить рекомендуемую длину админского и пользовательского ключа;
- документировать ротацию и восстановление ключей;
- добавить проверки допустимых значений в БД там, где они не мешают старым
  данным.

Критерий завершения: новая и существующая база обновляются одним повторно
запускаемым скриптом, а сохранность данных проверена автоматически.

### Этап 6. Планировщик маршрутов v2

Статус: **выполнен**.

Подробное ТЗ: `docs/REFACTORING_STEP_06_ROUTE_PLANNER_V2.md`.

Работы:

- определить измеримую целевую функцию: число опозданий, суммарное опоздание,
  простаивающие флоты, разброс нагрузки, разницу числа целей и суммарные прыжки;
- сохранить текущую эвристику как быстрый базовый вариант;
- добавить поиск улучшений после первого распределения: перестановки целей и
  обмены между флотами;
- сравнивать новый результат с базовым и никогда не принимать худший;
- добавить сценарии, в которых локально лучший выбор ухудшает общий план;
- показывать администратору метрики рассчитанного плана.

Критерий завершения: на фиксированном наборе сценариев v2 не увеличивает число
опозданий и улучшает хотя бы одну вторичную метрику относительно v1.

### Этап 7. Согласованность доски и истории

Статус: **выполнен**.

Подробное ТЗ: `docs/REFACTORING_STEP_07_OPERATIONAL_CONSISTENCY.md`.

Результат:

- итог, поставленный командиром флота, немедленно отражается на общей доске;
- после быстрого локального обновления выполняется контрольное чтение Supabase;
- завершённая строка автоматически остаётся видимой в истории;
- физическая очистка закрытых строк БД находится в панели главного
  администратора и выполняется только защищённой RPC.

### Этап 8. Целостность данных и проверка прав

Статус: **текущий**.

Подробное ТЗ: `docs/REFACTORING_STEP_08_DATA_INTEGRITY.md`.

Работы:

- строго отклонять невозможные даты вместо автоматической нормализации;
- исключить потерю конкурентных изменений результата флота;
- хранить отдельное время фактического завершения;
- проверять SQL-права от ролей `anon` и `authenticated`;
- сократить время хранения чувствительных ключей в браузере;
- закрепить целостность клиентской зависимости Supabase.

Критерий завершения: ошибки дат и конкурентной записи обнаруживаются до порчи
данных, а тесты подтверждают реальные права клиентских ролей.

## 4. Порядок релизов

Каждый этап проходит одинаково:

1. Зафиксировать тестом исходное поведение или ошибку.
2. Выполнить только объём текущего ТЗ.
3. Запустить модульные и E2E-тесты на desktop и mobile.
4. Проверить `git diff` и изменения SQL на сохранность данных.
5. Обновить README, память проекта и статус roadmap.
6. Сделать отдельный коммит и push в `main`.
7. После публикации выполнить короткую проверку GitHub Pages.

## 5. Что не входит в текущий план

- перенос на отдельный сервер приложений;
- обязательный аккаунт EVE SSO;
- React/Vue и полноценная система сборки;
- копирование всего интерфейса DOTLAN или карты клиента EVE;
- Ansiblex, червоточины и ручные временные связи;
- автоматическое изменение положения флота по данным игрового клиента.
